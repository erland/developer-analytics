# GHCR Release Verification

Step 83 verifies that a published Developer Analytics release is actually
installable from GHCR, not merely successfully pushed.

## Intended package visibility

The release Compose quickstart is designed for end users who should not need a
GitHub Container Registry credential. Therefore the intended visibility of both
packages is **public**:

- `ghcr.io/erland/developer-analytics-web`
- `ghcr.io/erland/developer-analytics-backend`

GitHub package visibility is repository/package configuration and cannot be
reliably expressed in the Dockerfile or Compose file. After the first package
publication, set each GHCR package to public in GitHub Packages if it is not
already public.

The release verification intentionally logs out from GHCR and performs a fresh
anonymous pull. A private package therefore makes the verification fail instead
of silently requiring undocumented registry credentials.

## Release verification

After both matrix image publications complete,
`.github/workflows/publish-images.yml` runs `Verify clean GHCR installation`.

The job executes:

```bash
bash ./scripts/verify-ghcr-release.sh <release-tag>
```

The script:

1. removes locally cached release images,
2. logs out from `ghcr.io`,
3. pulls web and backend anonymously,
4. verifies the complete `x.y.z` tags,
5. verifies the corresponding `x.y` tags,
6. renders the release Compose configuration and confirms both `backend` and
   `worker` use the same published backend image,
7. inspects image configuration and Docker history for concrete assignments to
   runtime secret variables,
8. verifies OCI source metadata.

The script strips an optional leading `v` from Git tags, matching the semantic
version tags generated by `docker/metadata-action`.

## Stable and prerelease tags

The publication workflow already provides:

- `x.y.z` for releases,
- `x.y` for releases,
- `sha-...` for traceability,
- `latest` only for stable releases.

Prereleases therefore do not replace `latest`.

The clean-install verification checks version-specific tags rather than relying
on `latest`, which keeps release installation deterministic.

## Secret hygiene boundary

The runtime secrets:

- `GITHUB_CLIENT_SECRET`
- `GEMINI_API_KEY`
- `CREDENTIAL_ENCRYPTION_KEY`
- `DB_PASSWORD`

must be supplied when containers start. They are not Docker build arguments or
Dockerfile environment values.

The release verifier scans image configuration and complete image history for
concrete assignments to those variables. This is a pragmatic guard against
accidentally moving repository/deployment secrets into image layers.

GitHub secret scanning and push protection remain complementary repository-level
controls.
